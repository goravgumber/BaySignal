## Master project prompt

Design a credible, restrained B2B smart-parking operations platform for Indian malls, hospitals, offices, campuses, parking contractors and public parking. The product concept is a parking-state integrity and operations workspace: operators compare what gate observations say, what bay-level sensors/cameras observe, what reservations/sessions say and what staff report, then review conflicts with timestamps, source, freshness, confidence when measured, coverage and an auditable correction workflow. This is a hypothesis, not an established unique advantage. Existing Indian providers advertise substantial overlap in parking automation, ANPR, bay sensors, booking, payments and multi-site dashboards.

Use one coherent design system across public marketing, desktop operator console, tablet/attendant workflows and mobile driver screens. Light warm-neutral surfaces; slate/ink text; restrained teal/blue primary action; amber warning; red error; gray unknown; purple only for explicitly labeled Simulation/sample data. Inter/system sans for UI and restrained monospace for plates, bay codes and timestamps. No Orbitron, neon, glow, cyberpunk, decorative tickers, excessive gradients, glassmorphism or confetti. Use text and icon as well as color for status. Maintain accessible contrast, visible focus, 44–48px touch targets (larger in attendant mode), responsive layouts for 1440×900, 1366×768, ~1024px and 360–430px.

Keep these concepts separate everywhere: (1) facility presence: entered and no verified exit; (2) bay occupancy: a named physical bay observed by an appropriate bay-level camera/sensor; (3) movement: leaving a bay does not mean leaving the facility; (4) reservation: a time window, not evidence of arrival/occupancy; (5) evidence confidence: source, timestamp, freshness and measured confidence. Never infer per-bay occupancy from entry/exit ANPR alone. Never vacate an unrelated bay because a vehicle exited at the gate. Never mark facility exit because the vehicle left a bay.

The existing prototype has working login, facility/slot/reservation paths, a simulator, device records, alert APIs and some analytics endpoints. It has no production ANPR or occupancy inference, evidence reconciliation, real payment confirmation, persisted alert rules, dependable model metrics or verified MQTT connection. Its visual QR is not scannable. Label future functionality `Concept`, illustrative values `Sample data`, and synthetic simulator events `Simulation`. Use “Insufficient data” for unmeasured reports. Do not invent customers, deployments, uptime, model accuracy, certification, emissions savings, ROI or payment confirmation. For any model view, label the entire screen as a concept/sample and use no achievement target as accomplished. Show evidence/results only if measured sample data are explicitly identified.

Make navigation role-aware for platform admin, organization/facility owner, manager/supervisor, attendant/gate operator, analyst/reviewer and driver. Owners/admins use invitation or approval onboarding; never public unrestricted platform-admin sign-up. Design error, empty, loading, stale, disconnected, partial coverage and conflicting states alongside happy paths. The working product name is editable and not cleared for trademark/domain use.

## Group 1 — Public brand, marketing and authentication (screens 1–15)

Using the master project system, generate one named screen group with: (1) B2B landing page; (2) capabilities/how-it-works; (3) mall/hospital/office/campus use cases; (4) hardware and integrations; (5) security/data governance; (6) request demo/pilot; (7) distinctive split operator login; (8) invite acceptance/account activation; (9) invitation-led organization/facility onboarding; (10) forgot password; (11) reset password; (12) email verification; (13) expired session; (14) access denied; (15) first-time facility setup wizard. Keep name editable and label not-yet-implemented flows Concept. Avoid fake customers and security certification. Use short, practical copy and clear next actions. Show no public unrestricted admin sign-up.

## Group 2 — Operations shell and live parking (screens 16–29)

Generate one shared role-aware application shell and consistent desktop operator views: portfolio overview; single-site dashboard; live parking map with map/grid/table modes; zone and bay detail drawer; future facility/zone/slot configuration; camera coverage mapping; facility-presence/session ledger; reconciliation inbox ordered by impact and age; discrepancy detail with source/timestamp evidence timeline and correction reason; separate ANPR entry and exit monitors; low-confidence plate correction; vehicle/session lifecycle detail. Show distinct total capacity, available, occupied, reserved, unverified and vehicles confirmed inside. True connection/freshness state must be obvious. Map must never be blocked by a floating simulator. The simulator is a removable, explicit purple Simulation state with source label. Uncertain bay state shows source, confidence only when measured, freshness and camera/sensor coverage. Keep every unsupported workflow Concept.

## Group 3 — Reservations and operator experience (screens 30–44)

Generate reservation list, create form, detail, cancellation/conflict handling, waitlist, driver check-in, gate checkout/session completion, attendant quick-action mobile/tablet, manual plate lookup/correction, ticket/pass and print layout, booking confirmation/arrival instructions, driver booking lookup, driver session status, checkout/payment/receipt and help/accessibility/language. One primary action per driver screen, concise forms, back navigation and attendant-assisted alternative. Do not require app install, QR scan or voice. Do not create a fake QR: show a print/pass fallback until a signed/server-validated scannable pass exists. Payment remains clearly pending until a real provider confirms it. Distinguish leaving a bay from exiting the site. Mark non-backed screens Concept.

## Group 4 — Devices, incidents and model operations (screens 45–59)

Generate device/camera overview and detail/health history; camera setup/calibration and image-quality/coverage test; MQTT/integration configuration and truthful connection health; incident queue/detail/resolution history; persistent alert-rule configuration and notification preferences; ANPR recognition-quality dashboard; occupancy evaluation dashboard; human review/labeling workbench; model version/evaluation detail; staged release/rollback/deployment history; stale/disconnected/unavailable inference states. Explicitly label model screens Concept and all example measurements Sample data. Do not imply a working production model or real MQTT status. Future quality views may include precision, recall, F1, occupancy error, correction rate, latency and day/night/glare/rain/occlusion breakdown only as measured report fields; show “No evaluation data” by default.

## Group 5 — Analytics, finance and administration (screens 60–75)

Generate occupancy/utilization, historical demand/dwell, revenue/transactions, rate configuration, payment settlement/reconciliation, receipt/print, environmental impact with transparent methodology, user management, role/permission matrix, organization/facility management, audit explorer, integration/API settings, security/retention settings, profile/notification settings, search/command palette and report/export configuration. Every chart shows date range and source; distinguish live, historical, simulated and estimated data. If no genuine historical series exists, use Insufficient data or conspicuously labeled Sample data. Never fabricate trendlines, ROI, emissions, model accuracy, revenue, uptime or payment completion. Design buttons to reflect real capabilities; unsupported operations stay Concept.

## Group 6 — Shared states and responsive variants

Create a reusable state library and variants: loading/skeleton, empty, no facility, no reservations, no device heartbeat, socket disconnected, stale last update, partial camera coverage, conflicting occupancy, uncertain ANPR, failed/unauthorized action, API/database unavailable, simulation active, confirmation/destructive dialog, network failure during booking/check-in/checkout. Also create critical mobile/tablet views for attendant check-in/checkout, plate lookup, discrepancy review and driver booking/session. State recovery options must match actual capabilities. Never silently resolve conflict to available/exited; preserve source evidence and ask authorized staff to review.
